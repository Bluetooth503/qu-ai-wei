# 保护清单与事实账本

改写的底线：**不新增事实、不删核心事实、不改变责任主体。** 本文件定义哪些内容默认不动，以及如何核对改写是否漂移。

## Protected spans（默认优先保留）

除非用户明确要求改风格且改动不损害信息，以下内容一律保留原样：

- 引用原文、命令、接口名、参数名、字段名、配置项
- 日志、报错、代码标识符
- 技术文档里的系统行为主语（「系统会自动重试」的「系统」）
- postmortem / incident / PRD / release note 中的专业术语
- 承载关键事实的抽象句，即使它「有点像 AI」——信息先于风格
- `code-context` 里的真实运行行为、适用条件和边界说明。清理注释/docstring/commit message 时，只去姿态词并保留这些信息；不能因为相邻行已有指标或结果就认定它们重复、整行删除

## 事实账本（改写前在心里记下，回读时逐项核对）

### 1. 数量—对象配对
数字和它修饰的对象必须一起保留。

- `两个团队` 不能写成「换过两个团队」（变了对象）
- 无源论断里的数字：`40%` 不能删掉后改成「会更快」；`未来十年` 不能改成「未来几年」。删整条可以，改值不行

### 2. 主体—目标配对
每个主体和属于它的动作/目标要绑定。

- 只属于企业的目标不能顺手并给开发者
- 删掉 `显著 / 大幅` 等渲染词时，仍要保留原文实际声称发生了什么

### 3. 谓词的方向、完成态、强度和效果类型
这些属于关系信息，不是修辞：

- `性能提升 / 体验改善 / 安全性加强` 不能弱化成「涉及这些方面」
- `提升效率` 不能顺势扩写成「节省时间 / 成本」
- `已经改善` 不能写成 `涉及`，`完成` 不能写成 `开始`

### 4. 同段共现 ≠ 能力关系
背景、主题或相邻句共现不等于能力关系。

- 同段提到 AI 和中文表达工具，不能据此写成「处理 AI 生成文本」
- 任何 `X 用来做 Y / X 基于 Y / X 处理 Y` 都必须能在原文谓词里找到依据
- 原文没有具体能力、实现关系或对象时：允许保留原来的抽象层级、缩短或标注缺口，**不能用看似合理的新事实补落点**

### 5. 目的、适用条件、风险和限制是信息
即使对象仍然抽象，也不能删：

- `为了解决这一痛点` 可以压成 `为了解决这个问题`，但不能因为没写具体问题就把「解决问题」这一目的删掉

### 6. 抽象层级不得擅自具体化
- `方案` 不能改成 `工具 / 产品`
- `目标` 不能改成 `产品`
- 描述某种架构的潜力，不能写成「系统基于该架构构建」

### 7. 中英混排
英文词按当前句子的实际语义判断，不机械套英文词表。

## 误杀防护的决策顺序

拿不准时按这个顺序问自己：

1. 这是 protected span 吗？→ 保留
2. 改写会改变事实账本里的配对关系吗？→ 不改，或改成不改变关系的写法
3. 这是句式壳还是信息句？→ 只有句式壳才动
4. 删掉后信息点还在吗？→ 不在就不删（bounded 下进删除清单交用户确认，in-place 下标注不删）

「像人」不能把文本改得更假。专业文本可以专业，关键是别模板化、别表演化。
