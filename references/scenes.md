# 场景判定与分场景规则

## 主场景（四选一，先判主场景再处理局部问题）

混合文本只保留一个主语域，其他语域只在必要信息层面留下。

### chat
**信号：** 短回复、日常对话、协作沟通、评论、即时反馈。允许口语，但不该端着说话。
**默认档位：** minimal

### status
**信号：** 站会更新、进度同步、复盘摘要、汇报式状态说明。重点是时间线、动作、结果、风险。
**默认档位：** minimal 或 standard
**禁改：** 时间线、完成态（已上线/未上线）、责任归属、数字（进度百分比）不能漂；不替人做心理判断，不做「方向没问题/不用太担心」式弱安抚（只能删除或标注「现有信息不足以判断」）。

### docs
**信号：** 操作文档、技术说明、接口说明、FAQ、事故复盘。重点是可检索、可复现、术语稳定。
**默认档位：** minimal；默认不升 aggressive
**禁改：** 命令、接口名、参数名、字段名、配置项、日志、报错、系统行为主语、技术报告术语。清理注释/docstring/commit message 时只去姿态词，不因相邻行已有指标就认定重复而整行删除。

### public-writing
**信号：** 公众号、小红书、公开帖、对外文章、观点写作。重点是语域一致，不要装「有洞见」。
**默认档位：** standard

## 子场景包（命中即补看，不依赖用户明说，不受主场景初判限制）

子场景只负责发布目的和语气收束，不覆盖 protected spans、Tier、档位和回读规则。

### README
**信号：** 项目介绍、快速开始、安装方式、功能列表、README intro。
**要求：** 第一屏说清「这是什么、给谁用、解决什么问题」。不写空洞的愿景宣言。

### release-note
**信号：** 版本标题、`Release Highlights`、`Added / Changed / Fixed / Tested`、changelog 列表。
**要求：** 列清本版变更、验证和限制，不写发布宣言。「激动人心的更新」类措辞删除，换成实际变更。

### forum-post
**信号：** Linux.do / V2EX / 社区帖 / 发帖复盘。
**要求：** 保留维护者的真实观察和社区语气，不改成公告腔。

### issue-reply
**信号：** issue / PR 回复、bad case、复现、下一版补 benchmark。
**要求：** 先确认问题和下一步，不做客服式安抚。「感谢反馈，我们会尽快处理」换成具体的时间点和动作。

### 小红书/社交帖
**要求：**
- 保留具体步骤、可保存的价值、短段落——这些是帖子成立的原因
- 避免假亲密（「姐妹们冲」「懂的都懂」式硬套）、夸大情绪拔高、互动诱饵
- 不因为平台奖励评论就硬加结尾问句
- 「可直接复制的 SOP」类套话换成实际的清单
- 话题标签可保留，但不能用来掩盖内容空洞

### 小说正文
**要求：**
- 稿内不输出分析（不要「这一幕体现了……」，那是编辑批注不是正文）
- 用动作、感官细节、后果代替「他意识到 / 不禁 / 微微 / 缓缓 / 心中暗道 / 脸色一变 / 嘴角微扬」——但这类陈词只在**不承载人物声音**时才删
- 对话可以保留粗糙、重复和简单词——如果那就是人物说话的方式
- 句式壳在对话里的豁免：`先…再…` 若听起来像职场压力或人物逻辑可以留；叙述层要严格

## 场景 × 档位速查

| 场景 | 默认档位 | 可否升 aggressive | 无源引用默认模式 |
|------|---------|------------------|----------------|
| chat | minimal | 可 | rewrite-safe |
| status | minimal/standard | 谨慎 | audit-only |
| docs | minimal | 否 | audit-only |
| public-writing | standard | 可 | rewrite-safe |
