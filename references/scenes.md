# 场景层：语域下限与范围

场景决定「语气能口语到什么程度」，范围决定「结构能自由到什么程度」。同一个句子在 chat 里可以口语化，在 docs 里必须保留术语和系统主语。白名单纪律不变：只改命中规则的地方，其余逐字保留。

判断前先看有没有目标风格文档（写作风格指南、语言特征分析、`语言DNA.md`）。有就先读，并把其中的句长、标点、用词习惯作为场景判断的一部分；风格文档与规则冲突时以它为准。

## 主场景（四选一）

混合文本只保留一个主语域，其他语域只在必要时留下信息。

### chat
**信号：** 短回复、日常对话、协作沟通、评论、即时反馈。
**底线：** 允许口语，但不端着说话。
**默认：** 范围 `structural`，力度 `minimal`，无源引用 `rewrite-safe`。

### status
**信号：** 站会更新、进度同步、复盘摘要、汇报式状态。
**重点：** 时间线、动作、结果、风险。
**禁改：** 时间线、完成态（已上线/未上线）、责任归属、进度数字不能漂；不替人做心理判断，不做「方向没问题/不用太担心」式弱安抚（只能删除或标注「现有信息不足以判断」）。
**默认：** 范围 `bounded`，力度 `minimal` 或 `standard`，无源引用 `audit-only`。

### docs
**信号：** 操作文档、技术说明、接口说明、FAQ、事故复盘。
**重点：** 可检索、可复现、术语稳定。
**禁改：** 命令、接口名、参数名、字段名、配置项、日志、报错、系统行为主语、技术报告术语。清理注释/docstring/commit message 时只去姿态词，不因相邻行已有指标就认定重复而整行删除。
**默认：** 范围 `bounded`，力度 `minimal`，**默认不升 aggressive**，无源引用 `audit-only`。

### public-writing
**信号：** 公众号、小红书、公开帖、对外文章、观点写作。
**重点：** 语域一致，不要装「有洞见」。
**默认：** 范围 `structural`，力度 `standard`，无源引用 `rewrite-safe`。

## 子场景包（命中即补看，不依赖用户明说）

子场景只负责发布目的和语气收束，不覆盖 protected spans、范围和力度规则。

### README
**信号：** 项目介绍、快速开始、安装、功能列表。
**要求：** 第一屏说清「这是什么、给谁用、解决什么问题」。不写空洞愿景宣言。

### release-note
**信号：** 版本标题、Release Highlights、Added / Changed / Fixed / Tested、changelog。
**要求：** 列清本版变更、验证和限制，不写发布宣言。「激动人心的更新」类换成实际变更。保留前后差异。

### forum-post
**信号：** Linux.do / V2EX / 社区帖 / 发帖复盘。
**要求：** 保留维护者的真实观察和社区语气，不改成公告腔。

### issue-reply
**信号：** issue / PR 回复、bad case、复现、下版补 benchmark。
**要求：** 先确认问题和下一步，不做客服式安抚。「感谢反馈，我们会尽快处理」换成具体时间点和动作。

### 小红书 / 社交帖
**要求：**
- 保留具体步骤、可保存的价值、短段落——这些是帖子成立的原因
- 不搞假亲密（「姐妹们冲」「懂的都懂」式硬套）、不夸大情绪、不加互动诱饵
- 不因为平台奖励评论就硬加结尾问句
- 「可直接复制的 SOP」类套话换成实际清单
- 话题标签可保留，但不能用来掩盖内容空洞

### 小说正文
**要求：**
- 稿内不输出分析（不写「这一幕体现了……」，那是批注不是正文）
- 用动作、感官细节、后果代替「他意识到 / 不禁 / 微微 / 缓缓 / 心中暗道 / 脸色一变 / 嘴角微扬」——但这类陈词只在**不承载人物声音**时才删
- 对话可以粗糙、重复、用简单词——如果那就是人物说话的方式
- `先…再…` 若听起来像人物逻辑或职场压力可以留；叙述层要严格

## 场景 × 默认值速查

| 场景 | 默认范围 | 默认力度 | 可否升 aggressive | 无源引用默认 |
|------|---------|---------|------------------|-------------|
| chat | structural | minimal | 可 | rewrite-safe |
| status | bounded | minimal/standard | 谨慎 | audit-only |
| docs | bounded | minimal | 否 | audit-only |
| public-writing | structural | standard | 可 | rewrite-safe |

## 范围（scope）的定义

| 范围 | 可以做什么 |
|------|-----------|
| `structural` | 可以删、并、重排，仍须保留有效信息与作者意图。短文本默认 |
| `bounded` | 不直接删整句、不并句、不重排；纯空句可在正文后列「建议删除（待确认）」，正文中仍保留。中文公开长文约 1000 字以上默认 |
| `in-place` | 不删句、不并句、不重排；只在句内替换或删修饰。要求保句数时也不拆句 |

用户明确指定的范围优先。删除建议不能包含独有事实、动作、条件、作者判断或承担必要转场的句子。用户授权处理的整条无源论断可以提删除建议，数字与跨度随原句保留在建议里，不擅自改值。

力度 `minimal / standard / aggressive` 只表示「改多少处」，不改变保真或范围边界；不要为达到某档位强行改词。
